# 第一部分 全景：这是什么系统（Step 1）

## 1.1 系统定位

一句话：**给链宇（iscmtech）内部销售/销售管理/财务/PM 使用的企业级销售 CRM**，覆盖「客户资源 → 商机推进 → 合同签约 → 开票/回款里程碑 → 合同额预算 → 签单达成率」的销售全流程，并附带组织/员工/商品/字典/权限等主数据与系统管理能力。

- 使用者：销售（crm_MEMBER/EMPLOYEE）、销售经理/项目经理（crm_PM/MANAGER）、财务（crm_FINANCE）、系统管理员（super_admin）。
- 核心价值：把客户与商机过程数据、合同与回款结果数据、预算目标数据放在同一套口径里，支撑「过程管理 + 结果考核」。
- 不做什么：没有线索池/营销自动化、没有审批流引擎、没有真实回款流水（回款是里程碑派生视图）、没有多币种/多税率核算、没有消息中心/邮件通知（配置了 mail 但 `crm.mail.enabled=false`）。

## 1.4 角色 × 模块权限矩阵

权限来源有三层：
1. **功能权限**：`crm_permission` → `crm_role_permission` → `crm_user_role`，登录时随 JWT 下发；`super_admin` 在 `PermissionChecker` 中直接放行，`ADMIN` **不放行**（仅数据范围层把它当管理员）。
2. **兜底预设**：若某用户所有角色的权限集合为空，按 roleCode 注入 [RolePermissionPresets](file:///workspace/crm-main/src/main/java/com/crm/security/RolePermissionPresets.java#L21-L53) 中的 5 个预设。
3. **记录级数据权限**：`crm_data_permission` 位掩码（1 查看 / 2 编辑 / 4 删除），负责人/管理员天然全权。

## 1.6 全局工程约定（读代码前必须知道）

| 约定 | 实现 | 影响 |
|------|------|------|
| 统一响应 | `Result{code,message,data}`；成功 code=200 | 前端只认 200；401/1004/1005 踢登录，403 分「密码过期」和普通无权限 |
| 分页 | 两套：`PageResult{list,total,pageNum,pageSize}` 与 MyBatis `Page{records,total}` | 前端兼容 `list/records/rows` |
| 逻辑删除 | `@TableLogic deleted`，全局 `logic-delete-value=1`；但客户自定义 SQL 用 `deleted=id` | 两套删除语义并存，统计口径易错 |
| 乐观锁 | `@Version version` + MyBatis-Plus 拦截器 | 自定义 update SQL 未带版本校验 |
| 审计字段 | `MyMetaObjectHandler` 自动填 `createBy/updateBy/createTime/updateTime` | 导入/批量场景需手动 `setCreateFields` |
| 金额单位 | 合同/预算/里程碑：**元**；前端合同表单：**万元**（提交 ×10000）；商机：**万元**（但未转换） | 全系统最大口径风险点 |
| 时间 | `LocalDate` / `LocalDateTime`，Jackson `GMT+8`、`yyyy-MM-dd HH:mm:ss` | 日期筛选按服务器时区 |
| 字典 | `crm_dict`（类型）+ `crm_dict_item`（项），支持 `systemType=PMT/SYSTEM/HR` | 页面下拉几乎全部依赖字典；缺字典会造成空下拉 |
| 数据隔离 | 商机/合同/项目/预算/回款按 `company_id`；客户不按；登录 JWT 的 companyId 传 null，服务层回退 1L | 多公司场景客户串数据；其他模块实际也集中在公司 1 |

- 前端年份只提供「今年往前 3 年」，没有财年表联动。
- 报表无行级数据权限，任何有报表权限的人看全公司。

## 2.11 模块 K：记录级数据权限（横切）

### 业务目标
在「功能权限」之外，控制单条客户/商机/合同/项目数据能被谁查看、编辑、删除、共享。

### 机制

| 能力 | 实现 |
|------|------|
| 权限位 | `READ=1`、`UPDATE=2`、`DELETE=4`，组合 3=可编辑、7=全权 |
| 数据表 | `crm_data_permission(module,biz_id,grantee_id,perm_bits,expire_date,company_id,granted_by)` |

## 3.2 跨模块数据流长链路（3 条）

### 链路 1：客户 → 商机 → 合同 → 里程碑 → 回款/预算/达成率（主价值链）

```text
① 客户创建（crm_customer）
   POST /crm/customers → 编码唯一 → follower/manager 归属
        │ customer_id
        ▼
② 商机创建（crm_opportunity）
   POST /opportunity → OPP-日期-序号 → stage=STAGE_01(5%) → status=IN_PROGRESS
        │ amount（万元，未转换）
        ▼
③ 商机推进/转合同
   change-stage → STAGE_07 自动 WON
   build-contract → 生成 crm_contract(UNSIGNED, amount=opp.amount)
                  → crm_contract_opportunity
                  → 商机阶段 STAGE_06(90%)
        │
        ▼
④ 合同补全 + 里程碑（crm_contract_milestone）
   合同金额变更 → 按 payment_ratio 重算里程碑金额/预计回款
   里程碑合计比例必须 100%
        │
        ├──► ⑤ 回款视图（PaymentMapper：已签合同 + 里程碑）
        │      状态 PAID/OVERDUE/UNPAID；首页回款指标同源
        │
        └──► ⑥ 预算计算（BudgetCalculateServiceImpl）
               本财年合同 → 签约月归属 → crm_budget_sheet/line/period_amount
                    │
                    ▼
               ⑦ 达成率（AchievementRateServiceImpl）
                  实际=已签合同 sign_date 金额；目标=101 科目预算期间金额
                  输出月度/累计达成率、缺口、KPI
```

**断点/风险**
- ③ 金额单位断点：商机万元直接进合同元 → ④~⑦ 全部金额缩小 1 万倍。
- ③ 合同号用秒级时间戳，高并发可能重复（有唯一索引兜底但会直接报错）。
- ④ 里程碑金额在前端保存时按 `currentContract.contractAmount × 比例` 重算，后端新增也按合同额×比例；两条路径一致，但合同金额单位错误会传导。
- ⑤ 只统计 `SIGNED`，`COMPLETED` 合同回款消失。
- ⑥ 预算计算是「全量重建」：删除该版本全部历史再插入，任何手工调整都会丢。
- ⑦ 目标只认 101 科目合同额预算，实际只认 sign_date，未签合同不计。

### 链路 2：登录 → JWT → 路由 → 菜单 → 按钮 → 数据行（权限链）

```text
① POST /auth/login
   crm_user 校验（状态/锁定/BCrypt）→ 角色码 → 权限码 → 父权限补全 → 预设兜底
        │
        ▼
② JWT（userId, username, companyId, orgId, roles, permissions）
   30 分钟；剩余 <50% 时 New-Token 滑动续签
        │
        ▼
③ 前端 Pinia（token/userId/realName/roles/permissions）
   持久化 localStorage：fs_user（token/userId/username/realName/avatar/tokenIssuedAt）
        │
        ├──► ④ 路由守卫 router.beforeEach
        │      - 无 token → /login?redirect
        │      - 未拉权限 → GET /auth/info → setPermissions
        │      - hasRoutePermission(path)：routePermissionMap 精确匹配
        │      - 未登记路径 → 直接放行（/payment、/project、/customer/子视图、/system/sync-config）
        │
        ├──► ⑤ 侧边菜单 filterMenus
        │      - 叶子按 permission 过滤
        │      - 分组只要还有子项就显示（父 permission 不生效）
        │
        ├──► ⑥ 按钮 v-permission / usePagePerms
        │      - hasPermission 支持「父级前缀匹配」：检查 crm:customer 时，只要拥有 crm:customer:view 等任一子权限即通过（用于菜单分组）
        │      - 各页混用 add/edit/delete 与 create/update/delete
        │
        └──► ⑦ 记录级 permBits（1/2/4/7）
               - 列表接口批量返回
               - 行内编辑/删除/共享按钮判断
               - 后端 assertWrite 二次校验
        │
        ▼
⑧ 后端 @PreAuthorize("@permissionChecker.hasPermission('crm:xxx:yyy')")
   - super_admin 放行
   - ADMIN 不放行（只有 DB 配置）
   - 403 → 前端提示或密码过期弹窗
```

**断点/风险**
- ④ 路由未登记路径绕过前端守卫；后端仍是最后防线。
- ⑤ 菜单父级 permission（`base`/`system`/`crm:customer`）与真实权限码不同，父级过滤形同虚设。
- ⑥ 权限码命名不统一：客户 `create/update/delete`，商机/合同/商品 `add/edit/delete`；自定义角色配错一个就出现「菜单可见但按钮不可用」或反之。
- ⑦ 共享入口缺失（客户/合同），导致后端能力无法使用。
- ⑧ JWT 内权限是登录快照，管理员改权限后用户不重登不生效。

### 链路 3：组织/员工/字典/区域 → 业务单据（主数据链）

```text
crm_org（树）
  ├─► crm_user.dept_id（用户归属，登录 JWT orgId）
  ├─► crm_employee.org_id（员工归属）
  ├─► crm_contract.org_id / product_line（合同产品线）
  └─► crm_budget_sheet.org_id / product_line_id（预算维度）

crm_employee
  ├─► 客户跟进人选择（/base/employees/active）
  ├─► 用户创建来源（/system/user/employees、add-from-employee）
  └─► HR 同步目标（当前空实现）

crm_dict / crm_dict_item
  └─► 所有页面下拉/标签（客户 16 类、商机 8 类、合同状态/开票、商品、组织/员工类型）

crm_region（四级）
  └─► 客户地址省市区（页面级联 + 导入名称→ID）
```

**断点/风险**
- 组织树只查 `status=1`，停用组织下的员工/合同在树中不可见但数据仍存在。
- 员工与用户两套表，工号/用户名关联弱，离职员工历史单据仍引用。
- 字典项删除无引用校验，历史单据可能显示原始 code。
- 区域初始化/导入依赖名称精确匹配，同名省市区用 `parentId|name` 兜底。

## 3.3 权限链路总览（一张表看清每层校验在哪）

| 层 | 校验点 | 代码 | 失败表现 |
|----|--------|------|---------|
| 传输层 | 无 token / token 过期/非法 | `JwtAuthenticationFilter` | HTTP 401 + `{code:1004/1005}` |
| 接口层 | `@PreAuthorize` 功能权限 | `PermissionChecker` | HTTP 403 + `{code:403}` 或业务 403 |
| 数据层（列表） | SQL 注入 currentUserId | 客户/商机/合同/项目 Mapper | 只能查到 owner/created/共享/跟进 |
| 数据层（单条写） | `assertWrite(module,id,bit)` | `DataPermissionServiceImpl` | 业务异常「无权操作该数据」 |
| 数据层（授权） | 管理员或负责人 | `DataPermissionServiceImpl.grant/revoke` | 业务异常「只有负责人或管理员可以授权」 |
| 前端路由 | `routePermissionMap` 精确匹配 | `router/index.js` | `/403`；未登记路径不拦 |
| 前端菜单 | 叶子 permission | `layouts/index.vue` | 菜单隐藏 |
| 前端按钮 | `usePagePerms` / `v-permission` | `stores/user.js`、`directives/permission.js` | 按钮移除/禁用 |
| 前端数据行 | `permBits` | 客户/商机/合同页 | 编辑/删除/共享按钮隐藏 |

> 结论：**后端是唯一可靠的权限边界**；前端三层（路由/菜单/按钮）都存在覆盖缺口，不能作为安全依据。
